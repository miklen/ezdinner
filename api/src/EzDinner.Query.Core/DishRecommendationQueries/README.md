# Dish recommendations

## Grocery offers and family settings

Implemented behind disabled-by-default acquisition gates. All 21 records in the captured Prej `/v1/chains` catalog are selectable, including border-trade and flyer-only chains. Source readiness is separate from selectability. The embedded catalog works without credentials; optional daily catalog refresh discovers subsequent chains. Previously saved chains absent from the catalog remain visible/removable but cannot be newly added. Seven successful evaluation requests captured representative Nemlig/REMA offers, observation rows, and the chain catalog on 2026-10-18; 18/25 daily calls remained. The supplied key was not persisted. No subscription, deployment, or complete live catalog refresh was performed.

`PUT /api/families/{familyId}/grocery-stores` accepts `{ "storeIds": ["nemlig", "rema1000"] }` and returns canonical sorted `{ "groceryStores": [...] }`. Existing Family Update permission authorizes owners; no new Casbin resources. Empty clears selection; duplicates normalize. Requests are bounded to 16 KiB and 100 IDs. Unauthenticated/unauthorized requests return 401, missing families 404, malformed or unsupported selections 400. Family reads add `groceryStores` and `supportedGroceryStores` descriptors (`id`, `name`, `isAvailable`, `isBorderTrade`, `isFlyerOnly`). Existing family writes patch member/name fields without replacing store selections; deploy this preservation to every writer before enabling edits. Old documents default to no selected stores.

### Configuration and rollout

Bind `GroceryRecommendations` (Azure setting keys use `GroceryRecommendations__Name`): `Enabled=false`, `CatalogRefreshEnabled=false`, `ApiKey` unset, `MaximumPages=50`, `MaximumOffers=5000`. Secrets belong in deployment secret configuration, never source or frontend. Offer acquisition requires Enabled and a key. Every chain in the Prej catalog is supported through the same adapter; the family selection controls which chains are queried. No per-store configuration is required. Catalog refresh requires its separate flag and key. Only chain IDs/product IDs go to Prej; family IDs, dishes, notes, and recipes do not. Profile inference uses existing Anthropic configuration.

Before production enablement, establish permitted daily caching, attribution and conditional price/location semantics, a sufficient subscription budget, and verified per-chain coverage. The 25/day evaluation tier is not an integration budget. Live verification gaps remain in the [design/source record](../../../../openspec/changes/add-grocery-offer-recommendations/design.md) and [sanitized fixtures](../../../../openspec/changes/add-grocery-offer-recommendations/fixtures/README.md). Do not count unverified chains as delivered merely because they can be selected.

After deploying the backend, call the existing `PUT /api/migrate` endpoint. Its grocery migration creates `GroceryRecommendationCache` with partition key `/scopeKey` and default TTL -1 (item expiration enabled, no default expiration). For an existing container, it corrects the TTL while preserving other container properties, using an ETag condition; subsequent runs leave a correctly configured container unchanged. An incompatible partition key fails rather than deleting/recreating the container. This endpoint also runs the existing family conversion and authorization migrations. No grocery-store data backfill or manual cache-container creation is needed. Deploy backend preservation/DTOs before the frontend; then run Cosmos acceptance tests and the authenticated selection-to-assignment loop. Roll back grocery influence with `Enabled=false`; retain preference-preserving family writers and saved selections/dinners. Optional settings UI can be hidden separately. No timer trigger or background polling is added.

### Acquisition, freshness and retention

The source reads bounded `/v1/offers` pages and joins `/v1/products/batch` price rows for `last_seen_date`; response `as_of` and retrieval time never extend freshness. Prices convert from integer øre to DKK. Reference price must exceed a positive offer price for the identical product, quantity/unit, chain and date window. AI-matched identities, conflicting package descriptions, mixed-species/prepared products and multi-buy prices cannot become raw exact-ingredient evidence. Missing required products or incomplete pagination abort publication and retain the previous complete snapshot. Unsupported products are omitted with partial coverage where mapping is uncertain. Membership/local restrictions remain an enablement gate. Attribution is shown as “Data: Prej”; absent verified product links stay null.

Each chain has a shared applicability scope. Successful snapshots, including successful empty results, are reused until the next 05:00 Copenhagen boundary. A persisted ETag-fenced claim reserves a five-minute cooldown before acquisition. Failed, cancelled, timed-out or abandoned attempts can be retried by a later recommendation request after that cooldown, including before 05:00, subject to the key-wide Prej cooldown below; there is no automatic retry loop. Concurrent requests and restarts share the cooldown, and crossing the daily boundary cannot bypass it. Missing initial snapshots may be acquired at any time. Legacy unpublished heads without `retryAfter` can recover on the next request without migration or manual deletion. Version pages publish before a conditional head switch; publication marks the attempt successful and clears the cooldown. Pages retain seven-day TTL and are bounded to 250 KB. `RefreshTimeoutSeconds=45` bounds each refresh within `SourceTimeoutSeconds=60` for the whole source read, including optional catalog retrieval. Configuration requires a refresh timeout of 1–90 seconds, a source timeout at least five seconds longer, and a source timeout no greater than 120 seconds. Acquisition uses two concurrent chain readers, four concurrent page requests per chain, 500 product IDs per batch, 2 MB per HTTP response and JSON depth 32. The first page failure cancels in-flight/queued pages and preserves the original exception. Ingredient inference gets a separate thirty-second budget after source retrieval; incomplete sources/profiles preserve ordinary recommendation eligibility and already usable evidence.

Every Prej HTTP request checks a persistent cooldown scoped by a SHA-256 identifier of the API key. A 429 honors `Retry-After` (seconds or HTTP date). A response reporting zero remaining daily calls, including a successful final response, blocks further calls until at least the next UTC midnight. A 429 with no usable retry header conservatively blocks until that midnight. The reset is persisted before returning the response, with a separate bounded write so caller cancellation cannot erase it. ETag-conditional updates only extend a block. The existing grocery container holds these nonexpiring `rate-limit` documents; this update needs no new container or migration. Stores, catalog requests and app restarts in the same database share the block. Development and production using the same key spend the same provider quota; if they use separate databases, each learns exhaustion from Prej's responses rather than sharing local reservations. Daily reset does not itself trigger acquisition: the next eligible recommendation request does.

Completed acquisition logs source/normalized counts, exclusion-reason counts and one public product ID per reason. Empty partial normalization is a warning. Malformed-field diagnostics identify the stage and field; failed HTTP requests log status and retry/quota headers. Query parameters, credentials, raw product content and family evidence are not logged. These diagnostics do not relax the rules for verified offers.

An observed cooldown blocks new requests in-process immediately, while its database write is pending. If persistence fails, the local block stays active, the persistence error is logged separately, and the original provider response is preserved. A failed database cooldown read prevents the outbound call. No additional Prej requests are made while the local or persisted deadline is active.

Known promotional end dates are inclusive in Europe/Copenhagen. Evidence expires at the earlier of 48 hours from source observation or midnight following the end date. Unknown expiry permits only the observation day. Current offers describe a purchase opportunity now, including for later dinners, not guaranteed future availability. Coverage distinguishes Fresh/Stale/Partial/Unavailable/Disabled/Unknown. Per-store freshness prevents one stale source relabeling another's fresh offers; expired evidence never boosts. A failed refresh can retain still-usable older evidence.

Ingredient profiles use family/dish/content-hash/model-prompt-vocabulary identity, fixed 30-day success TTL and 15-minute failure markers. Reads never renew TTL. Batches contain at most 10 dishes/40,000 serialized characters with at most three concurrent inference calls; a single oversized dish stays intact in its own batch. The model resolves saved notes before recipe text and title assumptions. Code rejects invalid categories, weights, references and factual excerpts absent from their cited source. Increment the profile version when changing inference semantics or vocabulary; extend compatibility and source mapping together with domain tests. Ratings, history and locale do not invalidate profiles.

Profile version ingredients-3 / vocabulary 3 delegates translation, synonyms, inflections, negation and family substitutions to the model across source languages. IngredientVocabularyFactory only defines canonical categories, incidental ingredients and compatibility; it has no translation or alias list. The model must quote the original source language verbatim, while code verifies the excerpt and source identity without English keyword matching. Semantic correctness and interpretation of family adaptations depend on the model; literal evidence validation is not an independent semantic verifier. Both versions participate in cache identity, so older profiles and rejection markers are reevaluated on demand.

### Recommendation response additions

`groceryCoverage.stores` adds one result per evaluated selected chain: `storeId`, catalog `storeName`, string `status`, and `usableOfferCount`. Counts describe usable source discounts before dish matching, not the number of displayed recommendation cards. The status card names zero-count stores with separate copy for unavailable checks, successful empty checks, partial coverage and stale observations, and suggests checking leaflets/apps/in-store manually. Older responses without `stores` remain accepted without inventing a store result. Appended ideas retain the latest available result for each still-selected store; an explicit refresh replaces the results. Store details are hidden while loading or when store/language changes require refreshing.

The recommendation endpoint additionally requires Family Read permission. `groceryCoverage` contains `status`, UTC `evaluatedAt` (nullable for legacy unknown), canonical sorted `storeIds`, and limitation codes. Each dish adds `groceryOffers`: source offer/store/product/ingredient identifiers and names, DKK `price`, nullable `referencePrice`, `discountFraction`, nullable ISO `validFrom`/`validThrough`, UTC `observedAt` and exclusive `usableUntil`, nullable HTTPS `sourceUrl`, `relationship` (Fact/Inference), conditions and freshness. Server evidence is authoritative for numbers/dates; inferred dish relationships remain Inference. Missing legacy additions decode as empty offers/Unknown coverage.

Offer points are capped at ten, strongest nonoverlapping opportunities only, and applied before automatic catalog limiting. Semantic batches/finalists see the same evidence; suitability remains user fit and a normalized server bonus is added once. Constraints and eligibility filters run first. Retained cards require explicit refresh after store/locale changes, More preserves conservative coverage, and one lifecycle-owned timer expires evidence without fetching or reranking. Successful refresh replaces results; failed refresh retains dismissal/browsing state.

See [implementation verification](../../../../openspec/changes/add-grocery-offer-recommendations/verification.md) for executed checks and outstanding live acceptance.

## Server-confirmed menu mutations

The workspace opts into `PUT /api/dinners/menuitem` and `/api/dinners/menuitem/remove` with `X-EzDinner-Mutation: conditional`. Payload: `familyId`, ISO `date`, `dishId`, and `expectedState` (`dishIds`, nullable `optOutReason`). Authentication and Dinner read/update permissions precede storage. Changed returns 200 with canonical `before`/`after` only after a successful ETag-conditional replace or create-if-absent; NoOp returns 200 without states, Conflict returns 409 without states. Payloads are bounded to 16000 characters and states to 100 dishes/500-character opt-out reasons. The resulting state is validated before persistence. Only Changed creates undo feedback or removes local wish feedback.

Calls without the header retain empty-200 success responses. Legacy add/remove/set-opt-out/remove-opt-out use bounded conditional retries, reloading and reapplying their intent after a concurrent write. All absent-day creators use the same stable family/date identity; loaded historical IDs are retained. Wish granting remains best effort after a successful assignment. Legacy bulk replacement/conversion operates on already persisted dinners and keeps its existing persistence behavior.

Automated checks and the remaining browser acceptance blocker are recorded in `openspec/changes/add-dish-first-week-planning/verification.md`. Controlled repository tests do not prove live Cosmos persistence or alternation with the existing Plan.

## Exploration metadata

The new workspace uses the optional `before=YYYY-MM-DD` parameter on the existing dish statistics endpoint to exclude that date and later assignments from serving history. Calls without this parameter retain the existing full-range behavior. Invalid boundaries return 400. The dish list adds `ratingCount` so the workspace distinguishes unrated dishes from rated dishes; the existing `rating` remains on its five-point scale. Recommendation results retain their documented ten-point rating scale and are converted for card display.

`POST /api/families/{familyId}/dish-recommendations` requires authentication and Dish, Dinner, and Wishlist read permissions for that family. It does not write dinners. Existing day/week planners keep their bindings and contracts.

Request fields: `selectedMonday` (ISO Monday), optional `targetDate` (Monday −2 through +6), `mode` (`automatic`, `request`, `more`), `locale` (`en`, `da`), `turns` (cumulative intent), `constraints` (editable current constraints), `excludedDishIds` (canonical GUIDs), and optional `role` (`Main`, `Side`, or null for all roles). Catalog filters must not be copied into conversational intent. The client explicitly selects recommendation scope independently.

Responses contain `outcome` (`Matches`, `NoMatch`, `Exhausted`, `NeedsClarification`), canonical dishes with factual history signals, historical reason kinds, localized provider explanations (`Fact` or `Inference`) and supplied source references, limitations, active constraints, and context summary. Names come from persisted dishes. More never recycles excluded IDs.

Default `DishRecommendations` configuration: `MaximumTurns=12`, `MaximumConstraints=12`, `MaximumRequestCharacters=4000`, `MaximumExclusions=1000`, `MaximumCandidates=300`, `MaximumEvidenceCharacters=100000`, `MaximumResults=6`, `ProviderTimeoutSeconds=30`. Boundary payloads are limited to 32000 characters. Provider output is limited to 32000 characters/4096 tokens. Candidate and evidence limits size individual batches, not the catalog. Every active nonexcluded candidate in the requested role/name scope is evaluated with its complete saved evidence and the same intent, constraints, and planning context. At most three provider calls run concurrently, each with its own timeout. A single dish exceeding the evidence target is sent intact on its own. Any failed or invalid batch fails the request instead of returning partial results. Batch matches are compared together by the provider when their combined evidence fits one batch; otherwise absolute suitability scores are merged globally, with history only breaking ties. No live recipe retrieval takes place. Large catalogs require more provider calls and may take longer or cost more.

Invalid requests return 400; unauthorized access returns 401 before evidence loading. Provider failures/malformed output return 502; timeouts return 504. Cancellation propagates. These errors are distinct from no-match and exhaustion. The existing Anthropic credential is reused by a dedicated adapter, with source text treated as evidence rather than instructions.

Automatic history uses distinct dates strictly before today's UTC calendar date. Leftovers count as separate servings but one recurrence occurrence. At least three occurrences establish median spacing. Ratings are null when absent. Scoring uses bounded rating/wish/recency/rotation/former-frequency contributions and deterministic name/ID ties. Initial weights are defaults, not learned family preferences.

`POST /api/families/{familyId}/dinners/{date}/undo-menu-change` requires Dinner update permission. Payload: `dishId`, `before`, `after`; each state contains `dishIds` and nullable `optOutReason`. The two states must differ by exactly that dish, represent an actual addition or removal, and the post-action state cannot have an opt-out. Ordinary undo requires current membership to match the action and preserves unrelated current dishes. Restoring a cleared opt-out requires the entire current day to match `after`. Duplicate additions are not reversible actions. Cosmos reads the current document ETag and replaces only with `IfMatchEtag`; concurrent storage changes and missing/stale days return HTTP 409 `{outcome:"Conflict"}`. Success returns `{outcome:"Restored"}`. Legacy unconditional save callers are unchanged.
