### Requirement: Week suggestions are produced by a swappable planner
The system SHALL route all week-suggestion requests through a single `IDinnerWeekPlanner` abstraction. The active planner SHALL be selected at application startup via configuration and SHALL NOT require code changes to switch.

#### Scenario: Rule-based planner produces week suggestions
- **WHEN** `Suggestions:Planner` config is `"RuleBased"` (or absent)
- **THEN** `IDinnerSuggestionService.SuggestWeek` returns suggestions ranked by the rule-based scoring engine

#### Scenario: AI planner produces week suggestions
- **WHEN** `Suggestions:Planner` config is `"Ai"`
- **THEN** `IDinnerSuggestionService.SuggestWeek` returns suggestions generated by the Anthropic API

#### Scenario: Unknown planner config defaults to rule-based
- **WHEN** `Suggestions:Planner` config value is absent or unrecognised
- **THEN** the system defaults to the rule-based planner and logs a warning at startup

### Requirement: AI suggestion logic is isolated from the Infrastructure layer
The AI week-planning orchestration (context assembly, prompt construction, result mapping) SHALL reside in `EzDinner.Query.Core`. Infrastructure SHALL contain only the HTTP adapter that sends a prompt to the Anthropic API and returns raw parsed output.

#### Scenario: Infrastructure adapter has no repository dependencies
- **WHEN** the `AnthropicWeekPlanClient` is inspected
- **THEN** it depends only on `AnthropicClient` (or equivalent HTTP client) and has no repository or service dependencies

#### Scenario: AI planner in Query.Core receives pre-assembled context
- **WHEN** `AiDinnerWeekPlanner.PlanWeek` is called
- **THEN** it receives a `FamilySuggestionContext` (dishes, dinners, wishlist) already assembled by `SuggestionContextAssembler`, and delegates only the API call to `ILlmWeekPlanClient`

### Requirement: Suggestion context assembly is shared between planners
Both planners SHALL receive dish, dinner, and wishlist data from a single `SuggestionContextAssembler` in Query.Core. Neither planner SHALL access repositories directly.

#### Scenario: Context assembler parallelises repository calls
- **WHEN** `SuggestionContextAssembler` assembles context for a week
- **THEN** dishes, historical dinners, and wishlist entries are fetched in parallel (e.g., `Task.WhenAll`)

#### Scenario: Both planners receive the same context type
- **WHEN** `RuleBasedDinnerWeekPlanner` and `AiDinnerWeekPlanner` are both invoked for the same family and week
- **THEN** both receive a `FamilySuggestionContext` of identical shape, ensuring consistent input regardless of active planner

### Requirement: `IDinnerSuggestionService` is the sole public suggestion API
The `IAiWeekPlannerService` interface and `AiPlanningQueries/` namespace SHALL be removed. All callers (including `AiWeekPlanFunction`) SHALL use `IDinnerSuggestionService.SuggestWeek` to retrieve week suggestions.

#### Scenario: AiWeekPlanFunction uses IDinnerSuggestionService
- **WHEN** `AiWeekPlanFunction` handles a POST request
- **THEN** it calls `IDinnerSuggestionService.SuggestWeek` and maps the `DaySuggestion` results to the existing `AiWeekPlanSuggestion[]` response model

#### Scenario: No references to IAiWeekPlannerService remain
- **WHEN** the codebase is searched for `IAiWeekPlannerService`
- **THEN** no references exist outside of deletion commits
